Какой фреймворк выберете для API и почему?¶

1. Ключевые задачи API¶

  • Обработка нескольких сотен запросов пользователей в реальном времени — система должна выдерживать одновременную работу сотен активных пользователей без деградации производительности и ухудшения пользовательского опыта.

  • Обеспечение real-time передачи данных — клиент должен получать ответ модели сразу после завершения вычислений, без необходимости постоянного опроса сервера и без задержек, влияющих на восприятие работы сервиса.

2. Что делегируем внешним компонентам¶

Чтобы снизить нагрузку на API-слой и сохранить его отзывчивость, мы выносим за его пределы:

  • Аутентификация пользователей — делегируется API Gateway (например, Kong, Traefik, NGINX с модулем auth). Gateway проверяет JWT-токен, извлекает идентификатор пользователя и пробрасывает его в заголовках к нашему API. Это разгружает бэкенд и централизует политики безопасности.

  • Синхронный вызов ML-API — не выполняется непосредственно внутри API-воркеров, а делегируется брокеру сообщений и отдельным воркерам. API только ставит задачу в очередь (с уникальным идентификатором task_id) и возвращает этот идентификатор клиенту. Воркеры забирают задачи, синхронно вызывают ML-API и сохраняют результат. Такой подход позволяет API-слою оставаться асинхронным и не блокироваться на время выполнения модели.

3. Дополнительные требования к API¶

  • Документирование — автоматическая генерация спецификации для согласования с фронтендом и onboarding новых разработчиков.

  • Версионирование — поддержка нескольких версий API одновременно для бесшовного обновления клиентов.

  • Авторизация — контроль доступа к эндпоинтам в зависимости от роли пользователя (выполняется уже на уровне самого API на основе данных из токена).

4. Критерии выбора фреймворка¶

Критерий

Почему это важно

Асинхронность

Позволяет одному воркеру обслуживать тысячи “висящих” соединений без блокировки. Критично при долгих ответах модели и для сохранения отзывчивости интерфейса.

Поддержка длительных соединений

Необходима для real-time доставки ответов клиенту без постоянного опроса, что улучшает пользовательский опыт. (Тип соединения — WebSocket или SSE.)

Работа с REST

Обеспечивает единообразие интерфейса, понятность для фронтенда и легкую интеграцию с существующими инструментами.

Автоматическая документация

Позволяет автоматически генерировать OpenAPI-спецификацию, что ускоряет разработку, упрощает тестирование и коммуникацию с командой.

Интеграция с брокерами сообщений

Необходима для асинхронной обработки задач (отправка запросов в очередь, получение результатов) без блокировки API-воркеров.

5. Почему FastAPI¶

FastAPI полностью соответствует всем перечисленным критериям:

  • Асинхронность — построен на ASGI, что позволяет одному воркеру обслуживать тысячи одновременных соединений. При долгих вызовах ML-API мы выносим задачи в брокер сообщений, не блокируя основные воркеры.

  • Длительные соединения — поддерживает Server-Sent Events (SSE) через StreamingResponse и WebSocket через встроенный WebSocket-класс. Это даёт гибкость в выборе протокола под конкретный сценарий.

  • REST — из коробки поддерживает все HTTP-методы, пути, параметры (query, path, header) и статус-коды. Позволяет строить полноценное RESTful API без дополнительных надстроек.

  • Автоматическая документация — генерирует OpenAPI-спецификацию на основе Pydantic-моделей. Swagger UI (/docs) и ReDoc (/redoc) доступны сразу после написания кода.

  • Брокеры сообщений — легко интегрируется с Redis, RabbitMQ, Kafka через асинхронные клиенты. Это позволяет строить асинхронные пайплайны без блокировки HTTP-воркеров.

  • Версионирование — поддерживается через группировку роутеров с префиксами (/api/v1, /api/v2), что позволяет одновременно поддерживать несколько версий API.

  • Авторизация — гибкие механизмы проверки прав позволяют реализовать ролевую модель на основе данных пользователя, переданных от API Gateway.

6. Сравнение с альтернативами¶

  • Flask — синхронный (WSGI), блокирует воркеры при долгих запросах. Требует множества дополнительных библиотек для асинхронности, валидации и документации.

  • Django — тяжёлый, синхронный, асинхронная поддержка пока нестабильна. Избыточен для нашего сценария.

  • Sanic — близок по производительности, но уступает FastAPI в экосистеме и интеграции с OpenAPI/Pydantic.

7. Итог¶

FastAPI выбран как оптимальное решение, так как он:

  • Асинхронный и масштабируемый

  • Поддерживает длительные соединения (SSE/WebSocket)

  • Работает с REST и автоматически генерирует документацию

  • Легко интегрируется с брокерами сообщений

  • Упрощает авторизацию и версионирование

Это позволяет решить все ключевые задачи API и заложить прочную основу для дальнейшего развития сервиса.
