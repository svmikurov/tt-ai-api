Как настроите права доступа к функциям сервиса?¶

Вступление (Постановка задачи)¶

Можно разграничить на уровни контроля доступа:

  • Уровень API: аутентификация пользователя (кто может вызывать)

  • Уровень эндпоинтов: авторизация для вызова (что именно он может вызывать)

  • Уровень данных: авторизация для доступа к данным (пользователь видит - только свое, аналитик - всех обезличенно)

  • Уровень инфраструктуры: доступ к серверам, БД, очередям (кто имеет доступ)

Аутентификация пользователя¶

В закрытом контуре без интернета я не могу использовать внешних провайдеров (Google, GitHub), поэтому выбираю внутреннюю JWT-аутентификацию:

  • Пользователь получает JWT-токен после логина (передаёт логин/пароль).

  • Токен подписывается асимметрично (RS256) или симметрично (HS256) с использованием секрета, хранящегося в K8s Secrets.

  • В каждом запросе клиент передаёт токен в заголовке Authorization: Bearer <token>.

  • Время жизни токена — 15–30 минут, а для долгих сессий используем Refresh Token (хранится в HttpOnly cookie или в отдельном хранилище).

Почему JWT, а не сессии в БД?¶

  • JWT самодостаточен — не нужно каждый раз ходить в БД за сессией, что критично при высокой нагрузке от сотен пользователей.

  • Легко масштабируется горизонтально (не нужен общий кэш сессий, как с Redis-сессиями).

  • В закрытом контуре мы можем безопасно хранить секрет на всех инстансах бэкенда.

Авторизация на уровне API (Что ты можешь делать?)¶

После аутентификации я проверяю права пользователя на выполнение конкретного действия. Здесь я использую ролевую модель (RBAC) с возможностью расширения до ABAC (атрибутный контроль) при необходимости.

Структура ролей:¶

  • Пользователь (User) — может отправлять запросы к ML-модели, просматривать свою историю.

  • Аналитик (Analyst) — дополнительно может смотреть агрегированную статистику по всем запросам.

  • Администратор (Admin) — управляет пользователями, настройками модели, просматривает логи.

  • Сервисный аккаунт (Service) — используется для внутренних вызовов (например, между микросервисами), имеет ограниченный набор прав.

Реализация в коде:¶

Использую декораторы или middleware во фреймворке (FastAPI/Django). Например, декоратор @require_roles(“admin”, “analyst”) навешивается на каждый эндпоинт.

Middleware проверяет:¶

  • Есть ли токен и валиден ли он.

  • Извлекает роль из payload токена.

  • Проверяет, разрешена ли роль для этого эндпоинта.

  • Если нет — возвращает 403 Forbidden.

Тонкий нюанс: Если один пользователь может иметь несколько ролей (например, “user” и “analyst”), я храню в токене список ролей и проверяю пересечение с разрешёнными.

Защита инфраструктурных функций (Доступ к сервисам)¶

Права доступа нужны не только на уровне API, но и к служебным функциям:

  • Health-эндпоинты (/health, /ready) — открыты без аутентификации (для оркестратора).

  • Метрики Prometheus (/metrics) — закрыты, доступ только у мониторинг-системы (через внутренний сетевой сегмент или токен).

  • Админ-панель (если есть) — доступна только админам, с дополнительным фактором (например, IP-белый список в закрытом контуре).

  • Swagger/OpenAPI документация — в проде я её отключаю или закрываю базовой аутентификацией, чтобы не светить контракты.

  • Миграции БД — запускаются отдельным init-контейнером с сервисным аккаунтом, который имеет права только на изменение схемы, но не на чтение данных пользователей.

Межсервисная аутентификация (Machine-to-Machine)¶

В нашем кейсе есть внешнее API модели. Наш бэкенд должен авторизоваться перед ним:

  • Использую сервисный аккаунт с долгоживущим токеном (или API-ключом).

  • Токен хранится в K8s Secrets и передаётся в переменную окружения MODEL_API_TOKEN.

  • При каждом запросе к модели добавляю заголовок X-API-Key: <token> или Authorization: Bearer <service_token>.

Если модель поддерживает mTLS (взаимную TLS-аутентификацию) — это ещё надёжнее: сертификаты тоже храню в Secrets и монтирую в контейнер.

Особенность закрытого контура: все сертификаты и ключи генерируются внутренним PKI (Public Key Infrastructure), никаких внешних центров сертификации».
