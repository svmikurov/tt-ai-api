Как упаковать приложение?¶

Приложение можно упаковать в Docker контейнер.

Использование Docker даст¶

Идентичность окружения¶

Помимо кода в контейнер упаковывается операционная система, переменные окружения, версии библиотек и рантайма (Python 3.8 or Python 3.13).

Без Docker: Приложение работает на Python 3.9, а на сервере стоит 3.11 — падает ошибка.

С Docker: Вы внутри контейнера используете Python 3.9, где бы этот контейнер ни запустили (на вашем ноутбуке, на сервере в облаке или на машине коллеги).

Изоляция ресурсов¶

  • У контейнера своя файловая система (он не видит ваши системные папки, если вы явно не разрешили).

  • У контейнера своя сеть (можно открыть порт 8080 внутри, даже если на хосте этот порт уже занят другим сервисом).

  • Вы не захламляете свою основную ОС установленных пакетов (все зависимости живут внутри образа и удаляются вместе с контейнером).

Легкость в настройке микросервисов¶

Если у вас база данных, брокер очередей (Redis) и само приложение — вы описываете их в файле docker-compose.yml. Все поднимается одной командой docker-compose up -d. Вам не нужно вручную настраивать соединения между ними, Docker создает внутреннюю сеть автоматически.

Сборка образа¶

Образ можно собрать в два этапа¶

  • Первый этап (builder) — здесь я устанавливаю все зависимости из requirements.txt с фиксированными версиями. При необходимости собираю нативные расширения (например, для некоторых ML-библиотек).

  • Второй этап (финальный) — беру чистый минимальный образ Python (например, python:3.11-slim), копирую в него уже установленные пакеты из первого этапа, а затем добавляю только сам код, миграции и вспомогательные файлы.

В результате финальный образ получается лёгким (без компиляторов и лишних утилит), безопасным (меньше поверхность для атак) и быстро загружается в закрытый контур.

Что кладу внутрь образа (Содержимое)¶

Внутрь образа я помещаю всё, что жёстко привязано к версии кода:

  • Исходный код — все .py файлы приложения.

  • Миграции базы данных (например, Alembic-скрипты) — они должны быть строго синхронизированы с версией кода.

  • Health-эндпоинты (/health, /ready, /live) — это часть самого приложения, потому что только оно знает, всё ли у него работает (БД подключена, ML-модель загружена).

  • Все Python-пакеты — они уже установлены на этапе сборки, поэтому при запуске контейнер не пытается ничего качать из интернета.

Что и как выношу наружу (Конфигурация и секреты)¶

Конфигурацию (адреса БД, порты, логирование) и секреты (пароли, ключи API) я выношу за пределы образа и передаю через:

  • Переменные окружения — для простых параметров вроде DATABASE_HOST, REDIS_PORT, LOG_LEVEL.

  • ConfigMap (в Kubernetes) — для групповой конфигурации, общей для всех подов.

  • Secrets (в Kubernetes) или HashiCorp Vault — для паролей, токенов, ключей шифрования. В закрытом контуре это могут быть внутренние системы управления секретами.

Такой подход позволяет использовать один и тот же образ для всех сред (dev, staging, production) — меняются только переменные. Это исключает ошибки типа “в проде забыли обновить конфиг”

Как управляю версиями и откатами¶

Каждый собранный образ я тегирую двумя способами:

  • Семантическим тегом (например, v1.2.3) — привязан к версии в Git.

  • Уникальным идентификатором сборки (например, sha-$(git rev-parse –short HEAD)) для точной трассировки.

Это позволяет:¶

  • Откатиться на предыдущую версию за секунды — просто меняю тег образа в манифесте Kubernetes и перезапускаю поды.

  • Точно знать, какой код работает в продакшене в любой момент времени.

Как упаковываю на уровне оркестрации¶

Помимо самого Docker-образа, я описываю всю систему в виде декларативных манифестов:

  • Для локальной разработки — docker-compose.yml, где описаны все сервисы (бэкенд, Redis, PostgreSQL, Nginx).

  • Для продакшена — Helm-чарт для Kubernetes. Это позволяет управлять всем приложением как единым пакетом: параметризовать конфигурацию, управлять репликами, обновлять по стратегии Rolling Update.

Вместе Docker-образ + Helm-чарт образуют полный установочный пакет, который можно развернуть в любой инфраструктуре одной командой.

Что делаю для разработчиков (DevX)¶

Чтобы упростить жизнь команде, я добавляю в репозиторий:

  • Makefile с командами make build (собрать образ), make up (поднять окружение), make test (запустить тесты в контейнере).

  • .env.example — шаблон со всеми необходимыми переменными окружения.

Это стандартизирует процесс и позволяет новому разработчику запустить проект за 2 минуты, даже не читая длинной документации».

Заключение¶

Упаковка приложения строится вокруг неизменяемого Docker-образа, который содержит код, миграции, health-чеки и все зависимости. Конфигурация и секреты передаются извне через переменные окружения и системы управления конфигурацией. Это даёт нам воспроизводимость, безопасность, быстрый откат, возможность работать в закрытом контуре и единый процесс для всех сред — от локальной машины разработчика до масштабируемого продакшена в Kubernetes.
