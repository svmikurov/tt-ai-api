========================================================
ADR-005: Использование Redis как брокера сообщений
========================================================

Статус
======

**Принято**

Контекст
========

Системе нужен брокер сообщений для:
- Очереди задач между API и Worker
- Хранения статусов задач
- Кеширования результатов

**Требования:**

- Быстрая работа (in-memory)
- Поддержка очередей (list/stream)
- Простая настройка

Решение
=======

Использовать **Redis** как брокер сообщений.

**Обоснование:**

1. **Скорость** — работает в памяти
2. **Простота** — легкая настройка
3. **Универсальность** — брокер + кеш + хранение статусов
4. **Интеграция** — хорошо работает с Celery и FastAPI

**Использование:**

- **Очередь задач:** `tasks` (list)
- **Статусы:** `status:{task_id}` (string)
- **Результаты:** `result:{task_id}` (string)

Последствия
===========

Положительные
-------------

- Высокая производительность
- Один сервис для нескольких задач
- Простая настройка

Отрицательные
-------------

- Хранение в памяти (ограниченный объём)
- Нет встроенной гарантии доставки (как в RabbitMQ)

Компромиссы
-----------

- Используем Redis вместо RabbitMQ (проще, меньше зависимостей)

Альтернативы
============

Альтернатива 1: RabbitMQ
------------------------

Более надёжный брокер с гарантией доставки.

**Причина отклонения:** Для нашего сценария достаточно Redis.

Альтернатива 2: Kafka
---------------------

Высокопроизводительный брокер для потоков.

**Причина отклонения:** Избыточен для нашего сценария.
