Статус
======

**Принято**

Контекст
========

Система обрабатывает запросы к ML-модели, которая может отвечать долго
(2-5 секунд). Клиенты должны получать результаты в реальном времени без
необходимости постоянного опроса (polling) сервера.

**Требования:**

- Клиент должен получать результат сразу после завершения обработки
- Клиент должен видеть промежуточный статус ("processing")
- Соединение должно быть устойчивым к разрывам

**Альтернативы:**

1. **Polling (HTTP GET /result)** — клиент периодически опрашивает сервер
2. **WebSocket** — двунаправленное соединение
3. **SSE (Server-Sent Events)** — одностороннее соединение от сервера к клиенту
4. **Long Polling** — удержание соединения до получения ответа

Решение
=======

Использовать **SSE (Server-Sent Events)** через библиотеку `sse-starlette`.

Техническая реализация
----------------------

Заголовки
~~~~~~~~~

.. code-block:: python

   return EventSourceResponse(
       event_generator(),
       headers={
           "X-Accel-Buffering": "no",  # критично для Nginx
       }
   )

Формат сообщений
~~~~~~~~~~~~~~~~

.. code-block:: python

   # Промежуточное событие
   yield {
       "event": "status",
       "data": "processing"
   }

   # Финальное событие с результатом
   yield {
       "event": "complete",
       "data": {"result": "...", "time": 2.34}
   }

Клиентский код
~~~~~~~~~~~~~~

.. code-block:: javascript

   const eventSource = new EventSource('/stream/{task_id}');

   eventSource.addEventListener('status', (event) => {
       console.log('Status:', event.data);
   });

   eventSource.addEventListener('complete', (event) => {
       const result = JSON.parse(event.data);
       console.log('Result:', result);
       eventSource.close();
   });

   eventSource.onerror = () => {
       console.error('Connection lost, reconnecting...');
   };

Последствия
===========

Положительные
-------------

- Real-time уведомления без опроса
- Простой клиентский API (EventSource)
- Автоматическое переподключение
- Низкая нагрузка на сервер

Отрицательные
-------------

- Нет двунаправленного обмена
- Максимум 6 соединений на домен в браузере
- Не поддерживается в старых браузерах

Компромиссы
-----------

- Используем одностороннее соединение вместо WebSocket
- WebSocket избыточен для нашего сценария

Альтернативы (отклонённые)
==========================

Polling
-------

Клиент опрашивает `/result/{task_id}` каждые 0.5-1 секунду.

**Причина отклонения:**
Высокая нагрузка на сервер при 200+ пользователях, задержка в доставке
результата.

WebSocket
---------

Полноценное двунаправленное соединение.

**Причина отклонения:**
Избыточен для нашего сценария, сложнее в реализации и поддержке.

Long Polling
------------

Удержание соединения до получения ответа.

**Причина отклонения:**
Сложнее в реализации, больше нагрузка на сервер.
