Способы длительного взаимодействия между сервером и клиентом
============================================================

WebSocket
---------

**Как работает**: Полноценный двусторонний (duplex) канал. Клиент отправляет запрос на апгрейд соединения
(через HTTP), после чего соединение "переключается" на **бинарный протокол** и остается
открытым постоянно.

**Особенности**:

- Сервер может сам инициировать отправку данных клиенту в любой момент.
- Низкий оверхед (заголовки минимальные после установки).
- Держит TCP-соединение постоянно открытым.

**Когда использовать**: ML-модель, чаты, онлайн-игры, биржевые котировки,
где нужна двусторонняя передача в реальном времени.



Server-Sent Events
------------------

**Как работает**: Клиент открывает долгоживущее HTTP-соединение через обычный GET-запрос
с заголовком Accept: text/event-stream.
Сервер отправляет данные потоком (chunked transfer), а клиент слушает события.

**Особенности**:

- Только односторонний канал: сервер -> клиент.
- Клиент НЕ может отправлять данные по этому же каналу (для отправки нужен отдельный HTTP-запрос).
- Автоматически переподключается при обрыве (встроенный механизм браузера).
- Работает поверх стандартного HTTP/2 (без проблем с прокси и корпоративными фаерволами).

**Когда использовать**: Ленты новостей, уведомления, стриминг логов, дашборды с обновляемыми графиками
(когда клиент только получает данные, а отправляет через обычный REST).



Long Polling
------------

(Устаревающий, но встречается)

**Как работает**: Клиент отправляет HTTP-запрос. Сервер не отвечает сразу, а держит соединение открытым
до тех пор, пока не появится ответ (или не истечет таймаут, например, 30 сек).
Как только сервер ответил, клиент тут же отправляет новый такой же запрос.

**Особенности**:

- Имитирует real-time поверх обычного HTTP.
- Огромный оверхед (каждый раз новые заголовки, повторная авторизация).
- Задержка между ответом и новым запросом.
- Неэффективно для сотен пользователей (много подвисших соединений).

**Когда использовать**: Легаси-системы, корпоративные прокси, которые блокируют WebSocket,
или если нужно поддерживать очень старые браузеры (IE10-).



gRPC Streaming
--------------

Для микросервисов и бекенда

**Как работает**: gRPC (на базе HTTP/2) поддерживает 4 типа вызовов, включая Server Streaming
(сервер шлет поток ответов) и Bidirectional Streaming (двусторонний поток).

**Особенности**:

- Бинарный протокол (Protobuf) — очень быстрый и компактный.
- Встроенная поддержка мультиплексирования (много потоков по одному TCP-каналу).
- Плохо поддерживается напрямую в браузерах (требуется gRPC-Web или прокси Envoy).

**Когда использовать**: Для внутреннего общения между микросервисами (бекенд-бекенд).
Если у вас SPA с фронтом на React, обычно используют gRPC-Web через прокси.
