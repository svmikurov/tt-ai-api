==========================================================
ADR-001: Выбор FastAPI в качестве основного веб-фреймворка
==========================================================

Статус
======

**Принято**

Контекст
========

Необходимо разработать бекэнд для сервиса взаимодействия клиента с ML-моделью.

От клиентов в реальном времени поступают сотни запросов к ML-модели.
Клиенты ожидают ответ модели в реальном времени.

ML-модель работает синхронно: один запрос — один ответ.
При поступлении нового запроса, пока старый обрабатывается,
новые запросы отбрасываются.

**Сервис должен**:

- Описывать контракты запросов и ответов (OpenAPI/Swagger).
- Поддерживать версионирование API.
- Хранить профили пользователей и историю сообщений.
- Иметь систему прав доступа к сервису.

Решение
=======

Выбран FastAPI в качестве основного веб-фреймворка.

**Обоснование**:

- Асинхронная архитектура FastAPI позволит эффективно удерживать сотни одновременных соединений 
  (keep-alive) во время ожидания ответа от синхронной ML-модели.
- Встроенная валидация через Pydantic сократит время разработки.
- Автоматическая генерация OpenAPI-документации упростит интеграцию с клиентами.
- Версионирование API будет реализовано через префиксы в путях (например, /v1/...).
- Встроенная поддержка WebSocket и Server-Sent Events (SSE) позволит в будущем
  организовать стриминг ответов клиентам без смены фреймворка.
- Система авторизации FastAPI (Depends) позволит гибко подключить существующую систему прав доступа.

Последствия
===========

**Положительные**:

- Возможность вынести в отдельный процесс отправку запроса к ML-модели.
- Быстрая разработка контрактов за счет автогенерации документации.

**Отрицательные**:

- Асинхронный код сложнее в отладке.
