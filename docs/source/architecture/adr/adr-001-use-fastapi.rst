========================================================
ADR-001: Использование FastAPI
========================================================

Статус
======

**Принято**

Контекст
========

Необходимо разработать бэкенд для сервиса взаимодействия с ML-моделью.

**Требования к фреймворку:**

- Асинхронная обработка запросов
- Поддержка длительных соединений (SSE)
- Автоматическая генерация документации (OpenAPI)
- Встроенная валидация данных
- Интеграция с брокерами сообщений
- Высокая производительность

Решение
=======

Использовать **FastAPI**.

**Обоснование:**

1. **Асинхронность (ASGI)** — позволяет одному воркеру обслуживать тысячи "висящих" соединений без блокировки
2. **SSE** — встроенная поддержка Server-Sent Events через `StreamingResponse`
3. **OpenAPI** — автоматическая генерация документации (Swagger UI, ReDoc)
4. **Pydantic** — встроенная валидация и сериализация
5. **Dependency Injection** — чистая архитектура и тестируемость
6. **Производительность** — один из самых быстрых Python-фреймворков

Последствия
===========

Положительные
-------------

- Высокая производительность
- Отличная документация и сообщество
- Встроенные инструменты (валидация, DI, OpenAPI)
- Легкая интеграция с Celery, Redis, SQLAlchemy

Отрицательные
-------------

- Меньше встроенных решений, чем в Django
- Требует понимания ASGI

Компромиссы
-----------

- Выбрали FastAPI вместо Django (слишком тяжёлый) и Flask (слишком простой, требует много доп. библиотек)

Альтернативы
============

Альтернатива 1: Django
----------------------

Тяжёлый, синхронный, асинхронная поддержка пока нестабильна.

**Причина отклонения:** Избыточен для нашего сценария.

Альтернатива 2: Flask
---------------------

Синхронный (WSGI), блокирует воркеры при долгих запросах.

**Причина отклонения:** Требует множества дополнительных библиотек для асинхронности и документации.
