ADR-006: Чистая архитектура (Clean Architecture)¶

Статус¶

Принято

Контекст¶

Система должна быть: - Тестируемой - Поддерживаемой - Гибкой к изменениям

Решение¶

Использовать Clean Architecture с разделением на слои:

  1. Domain/Application — бизнес-логика (Use Cases)

  2. Infrastructure — внешние зависимости (БД, брокеры)

  3. Entrypoints — API (FastAPI)

Структура:

src/sd/
├── api/           # Entrypoints (FastAPI)
│   ├── entrypoints.py
│   ├── containers.py
│   └── use_cases.py
├── worker/        # Infrastructure (Celery)
│   └── tasks.py
├── broker/        # Infrastructure (брокер)
│   ├── abstract.py
│   ├── redis_broker.py
│   └── factory.py
└── ai_api/        # Entrypoints (AI API)
    └── ai_api.py

Принципы:

  • Зависимости только внутрь (от инфраструктуры к бизнес-логике)

  • Использование Dependency Injection

  • Интерфейсы (абстракции) для внешних зависимостей

Последствия¶

Положительные¶

  • Легкое тестирование (можно мокировать зависимости)

  • Замена брокера (Redis → Kafka) без изменения API

  • Чёткое разделение ответственности

  • Код легче поддерживать

Отрицательные¶

  • Больше файлов и структуры

  • Требует дисциплины от команды

Компромиссы¶

  • Используем Clean Architecture вместо монолита (сложнее, но гибче)

Альтернативы¶

Альтернатива 1: Монолит¶

Вся логика в одном модуле.

Причина отклонения: Сложно тестировать и поддерживать.

Альтернатива 2: Микросервисы¶

Каждый компонент как отдельный сервис.

Причина отклонения: Избыточно для проекта.
